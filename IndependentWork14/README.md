## 1. Мета роботи
Дослідити та проаналізувати реальні сценарії використання бібліотеки Polly для реалізації політик відмовостійкості (Retry, Circuit Breaker, Timeout) у .NET-застосунках.

---

## 2. Опис розроблених сценаріїв відмовостійкості

### Сценарій 1: Підключення до бази даних (Retry Strategy + Exponential Backoff + Jitter)
- **Проблема:** Під час пікового навантаження база даних може тимчасово скидати з'єднання (`DbException`) або перебувати в стані перевищення тайм-ауту пулу підключень.
- **Обрана політика:** `Retry` (3 спроби) з експоненційною затримкою (`Exponential Backoff`) та випадковим відхиленням (`Jitter`).
- **Обґрунтування:** Експоненційна затримка з джиттером запобігає «шторму запитів» (Thundering Herd Problem) на базу даних, даючи їй час вивільнити ресурси.

### Сценарій 2: Оплата через платіжний шлюз (Комбінація Timeout + Retry)
- **Проблема:** Зовнішні банки або платіжні сервіси можуть зависати під час транзакцій. Без таймауту потік застосунку блокується на невизначений термін.
- **Обрана політика:** Комбінований `ResiliencePipelineBuilder`: `AddRetry` + `AddTimeout(1.5s)`.
- **Обґрунтування:** Таймаут обриває завислий запит до банківського сервісу через 1.5 секунди, а `Retry` робить повторну спробу проведення платежу на суму в грн.

### Сценарій 3: Відправка SMS-сповіщень (Circuit Breaker)
- **Проблема:** Якщо зовнішній провайдер SMS повністю вийшов з ладу (повертає 503), постійні повторні спроби лише марно витрачають ресурси та сповільнюють систему.
- **Обрана політика:** `Circuit Breaker` (захисний вимикач).
- **Обґрунтування:** При перевищенні порогу помилок (50%) політика відкриває ланцюг (`OPEN`), миттєво відхиляючи нові запити без звернення до впалого сервісу. Через 3 секунди переходить у стан `HALF-OPEN` для перевірки відновлення.

## 3. Відповіді на контрольні запитання

1. **Коли доцільно використовувати Retry, а коли — CircuitBreaker або Timeout?**  
   - **Retry** використовується для тимчасових сбоїв (transient faults), які зникають самі по собі через частки секунди (короткі збої мережі).  
   - **CircuitBreaker** застосовують при тривалих або каскадних аваріях сервісу, щоб не навантажувати систему марними запитами, коли сервіс точно "лежатиме" певний час.  
   - **Timeout** необхідний для гарантування верхньої межі часу очікування відповіді, щоб запобігти витоку потоків (Thread Exhaustion).

2. **Які переваги дає комбінування кількох стратегій у межах однієї ResiliencePipeline?**  
   Це дозволяє будувати багаторівневий захист (Defense in Depth). Наприклад, `Timeout` захищає від зависань, `Retry` перехоплює таймаути та повторює спробу, а `CircuitBreaker` зупиняє повтори, якщо сервіс не відповідає глобально.

3. **Чому для навчальних сценаріїв важливо логувати кожну повторну спробу та результат виконання політики?**  
   Логування дозволяє наочно побачити внутрішню механіку роботи Polly: момент виникнення винятку, проміжок затримки перед повтором (`RetryDelay`), переходи станів Circuit Breaker (`Open`, `HalfOpen`, `Closed`) та фінальний результат обробки.

4. **Які ризики виникають, якщо застосувати політику повторних спроб до неідемпотентної операції?**  
   Якщо операція не є ідемпотентною (наприклад, списання коштів з картки або створення замовлення в БД), повторна спроба після прихованої помилки мережі може призвести до **подвійного списання грошей** або дублювання даних, оскільки перша спроба могла успішно виконатися на сервері, але відповідь втратилася по дорозі.
