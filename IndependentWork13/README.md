## 1. Мета роботи
Дослідити стратегії відмовостійкості Polly на трьох різних навчальних сценаріях.

## 2. Реалізація
Назва проєкту `IndependentWork13` відповідає умові самостійної №14. Використано Polly 8.9.0 і API `ResiliencePipelineBuilder`. Усі сервіси імітуються локально лічильниками й винятками: зовнішні запити, зміни бази чи реальна відправка повідомлень не виконуються.

### Сценарій 1. Перевантажена черга повідомлень — Retry
**Проблема:** короткочасна недоступність черги. Перші два надсилання створюють `IOException`, третє успішне. Повторюються лише такі помилки; налаштовано до трьох повторів, експоненціальну затримку та jitter. Обмеження кількості запобігає нескінченному очікуванню. Лог містить номер спроби, причину та фактичну затримку.

```csharp
new ResiliencePipelineBuilder()
    .AddRetry(new RetryStrategyOptions
    {
        ShouldHandle = new PredicateBuilder().Handle<IOException>(),
        MaxRetryAttempts = 3,
        Delay = TimeSpan.FromMilliseconds(50),
        BackoffType = DelayBackoffType.Exponential,
        UseJitter = true
    }).Build();
```

Фактично було 3 виклики, 2 повідомлення про повтор і фінальне «Повідомлення прийнято». Ідентифікатор `msg-001` зберігається між спробами; у реальній системі отримувач має забезпечувати дедуплікацію за ним. Сам рядок MessageId у демонстрації не забезпечує дедуплікацію. Рандомізація Polly може давати нерівномірну послідовність затримок, тому кожна наступна затримка не зобов’язана бути більшою.

### Сценарій 2. Недоступна база — CircuitBreaker
**Проблема:** постійні запити до несправної бази створюють додаткове навантаження. Обрано автоматичне розмикання кола: при двох невдалих викликах протягом вікна 10 секунд (частка помилок 100%) воно переходить у Open на 1 секунду.

```csharp
new ResiliencePipelineBuilder()
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions
    {
        ShouldHandle = new PredicateBuilder().Handle<IOException>(),
        FailureRatio = 1.0,
        MinimumThroughput = 2,
        SamplingDuration = TimeSpan.FromSeconds(10),
        BreakDuration = TimeSpan.FromSeconds(1)
    }).Build();
```

Перші два запити викликають базу й отримують винятки. Третій відхиляється через `BrokenCircuitException` без звернення до бази. Після очікування 1.1 секунди наступний запит проходить пробу HalfOpen й успішно закриває коло. Фактичних викликів бази — 3 на 4 запити. `OnOpened`, `OnHalfOpened` і `OnClosed` показують переходи станів. CircuitBreaker не повторює операцію сам і не приховує початкові помилки.

### Сценарій 3. Повільне читання звіту — Retry + Timeout
**Проблема:** окреме читання може зависнути, але повтор іноді завершується швидко. Зовнішній Retry обробляє `TimeoutRejectedException`, внутрішній Timeout обмежує кожну спробу 200 мс. Дозволений один повтор після затримки 50 мс.

```csharp
new ResiliencePipelineBuilder()
    .AddRetry(new RetryStrategyOptions
    {
        ShouldHandle = new PredicateBuilder().Handle<TimeoutRejectedException>(),
        MaxRetryAttempts = 1,
        Delay = TimeSpan.FromMilliseconds(50)
    })
    .AddTimeout(TimeSpan.FromMilliseconds(200))
    .Build();
```

Перша спроба очікує 600 мс і скасовується тайм-аутом, друга триває 30 мс і завершується. `Task.Delay` отримує `CancellationToken` від Polly. Тайм-аут є кооперативним: без обробки токена політика не може примусово зупинити довільну роботу. Тут обмежено кожну спробу, а не загальний час усіх повторів; для загального ліміту потрібен ще зовнішній Timeout.

## 3. Відповіді на контрольні запитання
1. **Коли застосовувати стратегії?** Retry — для тимчасових збоїв; CircuitBreaker — щоб тимчасово припинити навантаження на несправний ресурс; Timeout — для обмеження очікування операції.
2. **Переваги комбінації?** Можна одночасно обмежити тривалість спроби та повторити тимчасову помилку. Порядок додавання визначає вкладеність і поведінку.
3. **Навіщо логування?** Воно показує, які виклики реально виконувались, які блокувались, чому відбулися повтори та який фінальний результат.
4. **Ризики неідемпотентних операцій?** Повтор може двічі списати кошти або створити повідомлення, навіть якщо попередня відповідь загубилась після успіху. Потрібні ключі ідемпотентності, дедуплікація та вибіркова обробка тимчасових помилок.

## 4. Запуск і вивід
Із кореня репозиторію (.NET SDK 10). Перший запуск потребує відновлення пакетів NuGet:

```powershell
dotnet run --project IndependentWork13
```

Приклад завершення третього сценарію:

```text
Завантаження звіту, спроба 1
Спроба перевищила ліміт 200 мс.
Повторюємо читання звіту після тайм-ауту.
Завантаження звіту, спроба 2
Звіт завантажено.
```

## 5. Висновок
Polly дозволяє відокремити політику відмовостійкості від бізнес-операції. У трьох сценаріях показано повтори, блокування несправного ресурсу та тайм-аут із повтором. Вибір помилок, лімітів, порядку стратегій і способу скасування залишається відповідальністю розробника.
